# Анализ кейса 1: Career Quest

## Вывод для MVP

Нужно сделать веб-приложение для сотрудника и HR. Сотрудник выбирается из загруженного датасета, видит профиль, текущий грейд и цель, разрывы по навыкам, историю активностей и 1–3 следующих шага. Для каждого шага приложение показывает доказуемое объяснение: требования целевого грейда, текущий уровень, закрываемые навыки, подходящую активность и сигналы из истории. После отметки активности как выполненной пересчитываются уровни навыков и траектория. Вторая вкладка показывает HR-срез по проседающим навыкам и вовлечённости.

Основа рекомендации должна быть детерминированной. LLM нужен как слой формулировки и локализации объяснения, а не как единственный ранжировщик. Это защищает основной сценарий от непредсказуемых ответов модели и соответствует проверке на профилях, где однофакторная эвристика ошибается.

## Что требует кейс

Обязательные пользовательские сценарии:

1. Открыть произвольного сотрудника и увидеть роль, грейд, навыки, пройденные активности и доступные следующие шаги.
2. Получить 1–3 релевантные рекомендации.
3. Понять объяснение минимум по трём факторам: грейд, разрывы навыков, история участия, требования следующего уровня.
4. Отметить активность выполненной и увидеть изменение прогресса по навыкам и траектории.
5. Открыть простой HR-view: часто проседающие навыки, сотрудники без шага развития и участие по активностям.
6. Загрузить дополнительные профили и историю в формате стартового датасета.

Нефункциональные ограничения: интерфейс должен отвечать до 2 секунд, рекомендация — до 10 секунд; запуск — одной командой; данные синтетические и не должны покидать контур хакатона. Доступ сотрудника и HR нужно разделить, а вовлечённость одного сотрудника не показывать другим сотрудникам.

Геймификация, валюта, награды, признание коллегами, прогноз оттока, календарь, мобильная адаптация и полноценная локализация являются опциональными. В MVP их не включаем, если не останется время.

## Датасет

Стартовый кит содержит:

- 200 профилей сотрудников в `employees.json`;
- 40 активностей в `events.json`;
- 60 навыков и требования 8 ролей по 4 грейдам в `skills.json`;
- 2 743 записи истории участия в `activity_history.csv` за 24 месяца.

Важно учитывать правила датасета:

- отсутствующий навык равен уровню 0;
- шкала навыка — от 0 до 5;
- требования грейдов не снижаются;
- завершённая активность обычно не рекомендуется повторно, кроме регулярного клуба `EV_036`;
- prerequisite активности должны быть проверены до рекомендации;
- завершённые активности после `last_review_date` ещё не отражены в текущих уровнях навыков;
- оценка жюри загружает дополнительные профили и историю в той же схеме.

Для загрузчика нельзя зашивать 200 сотрудников или фиксированный список навыков. Все идентификаторы, поля и новые строки должны читаться из файлов.

## Предлагаемая логика рекомендации

### 1. Определить цель

- Если у сотрудника задан `career_goal`, использовать `target_role` и `target_grade`.
- Если цели нет, предложить следующий грейд в текущей роли.
- Если текущий грейд `Lead` и цель не задана, показать поддерживающий план навыков без утверждения о повышении.

### 2. Построить gap-профиль

Для каждого навыка целевого профиля вычислить:

```text
gap = max(required_level - current_level, 0)
```

Отдельно отметить `critical_skills` целевого грейда. В объяснении показывать текущий уровень, требование и размер разрыва.

### 3. Отфильтровать активности

Оставить только активности, которые:

- подходят роли и грейду сотрудника;
- развивают хотя бы один навык с положительным gap;
- проходят проверку prerequisites;
- не были завершены ранее, кроме `EV_036`;
- не являются обязательным комплаенс-процессом, если они не закрывают развивающий разрыв.

Если подходящих активностей нет, показать это явно и предложить обновить оценку навыков или выбрать цель.

### 4. Учесть историю

История должна влиять на ранг и объяснение:

- `completed` — не рекомендовать повторно и учитывать достигнутый опыт;
- `no_show`, `dropped`, `declined`, `overdue` — не считать навыком закрытым;
- повторный пропуск похожей активности — штрафовать и предложить другой формат или короткий шаг;
- свежая успешная активность может быть положительным сигналом для следующего шага;
- отрицательный сигнал не должен полностью скрывать критичный шаг, иначе сотрудник останется без траектории.

### 5. Ранжировать

Рекомендуемый прозрачный score:

```text
score = 0.45 * gap_coverage
      + 0.25 * critical_coverage
      + 0.15 * goal_alignment
      + 0.10 * history_fit
      + 0.05 * feasibility
```

Где:

- `gap_coverage` — доля закрываемого разрыва по уровням навыков;
- `critical_coverage` — покрытие критичных навыков целевого грейда;
- `goal_alignment` — совпадение с ролью, грейдом и карьерной целью;
- `history_fit` — учёт завершений, пропусков, отказов и предпочтительного формата;
- `feasibility` — отсутствие недоступных prerequisites, разумная длительность и наличие ближайшей сессии.

В UI score не обязательно показывать числом. Нужно показать факторы и их фактические значения.

### 6. Сгенерировать объяснение

Передавать LLM только структурированный безопасный контекст выбранного профиля, разрывов, истории и кандидата. Требовать JSON со списком фактов и коротким текстом на языке сотрудника. Проверять, что каждый факт есть во входном контексте; при ошибке использовать шаблонное объяснение.

Пример объяснения:

> `EV_006 Designing High-Load Systems` — при цели Senior у вас System Design 1 из 4 и API Design 1 из 4; активность закрывает оба критичных навыка на один уровень и доступна для Backend Engineer Middle. В истории `EV_006` ещё не завершалась, но были пропуски архитектурных активностей, поэтому следующим шагом лучше выбрать ближайшую доступную сессию и подтвердить участие.

## Демонстрационный сценарий

Для живой защиты удобно иметь два профиля:

- `E0002` Arman Zhaksylykov: Backend Engineer Middle, цель Senior. Критичные разрывы — System Design 1/4 и API Design 1/4. В истории есть и успешные, и неуспешные попытки, поэтому такой профиль показывает, что рекомендация учитывает не только минимальный навык.
- `E0028` Akmaral Ismailova: Backend Engineer Middle без цели. Система должна предложить следующий грейд в текущей роли и объяснить небольшие разрывы по Cloud, Containers, Observability и Teamwork, не выдавая рекомендацию по одному полю.

Для ручной проверки жюри нужно показать цикл:

```text
загрузка датасета → выбор сотрудника → цель и gaps → 1–3 рекомендации
→ раскрытие объяснения → отметить активность выполненной
→ пересчитанные навыки и прогресс → HR-срез
```

## Архитектура MVP

```text
JSON/CSV loader
    ↓
Domain layer: profiles, role requirements, events, history
    ↓
Recommendation engine: filters → gaps → scoring → evidence
    ├── deterministic API for profile and HR view
    └── optional LLM explainer with structured fallback
    ↓
Web UI: Employee view | Recommendation card | Progress update | HR view
```

Практичный стек для пяти часов: Python + FastAPI для API, React/Vite для интерфейса или один Streamlit-приложение, если команде важнее скорость. Для защиты предпочтителен простой веб-интерфейс с одной командой запуска. Хранилище можно сделать in-memory с сохранением состояния в локальный JSON; база данных не обязательна для MVP.

Минимальные API-операции:

- `GET /employees` — список и фильтр сотрудников;
- `GET /employees/{id}/trajectory` — профиль, gaps, history и рекомендации;
- `POST /employees/{id}/activities/{event_id}/complete` — применить gain и обновить состояние;
- `GET /hr/overview` — агрегированные gaps и участие;
- `POST /import` — загрузить дополнительные файлы в схеме датасета.

## План на 5 часов

1. 0:00–0:30 — зафиксировать схему, выбрать стек и проверить загрузку всех файлов.
2. 0:30–1:30 — реализовать доменные модели, goal resolution, gaps и фильтры prerequisites/history.
3. 1:30–2:30 — реализовать scoring, evidence и API для профиля и рекомендаций.
4. 2:30–3:30 — собрать экран сотрудника: профиль, trajectory, recommendation cards и complete action.
5. 3:30–4:15 — собрать HR-view и импорт дополнительных профилей/истории.
6. 4:15–4:45 — добавить LLM-explainer с безопасным fallback или аккуратный шаблон, если API нестабилен.
7. 4:45–5:00 — прогнать три тестовых профиля, проверить запуск одной командой, секреты, README и отправить финальный коммит.

## Критические риски

- Рекомендовать только самый низкий навык — ошибка на проверочных профилях. Нужны минимум gap + critical skill + history.
- Отдать ранжирование полностью LLM — риск неповторяемости и неподтверждённых утверждений. Сначала считать evidence кодом.
- Зашить демонстрационные профили — жюри загрузит другие данные. Нужен импорт и отсутствие фиксированных ID в логике.
- Показывать сотрудникам HR-данные друг друга — нарушение приватности. В MVP явно разделить режимы и скрывать историю вовлечённости от employee-view.
- Потратить время на награды и сложную геймификацию — это опциональная часть и не приносит баллы обязательного ядра.

## Критерии готовности перед сдачей

- Основной сценарий проходит от чистого запуска до обновления прогресса.
- Объяснение любой рекомендации ссылается минимум на три факта входных данных.
- Рекомендации не зависят от одного поля и меняются при изменении цели, навыка или истории.
- Дополнительный профиль и история загружаются без изменения кода.
- README содержит фактический стек, архитектуру, запуск, проверку и ограничения.
- В репозитории нет API-ключей, токенов, приватных файлов и реальных персональных данных.
